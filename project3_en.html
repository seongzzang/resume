Switching from a Messaging Model to Real-time Chat
Problem Identification
At launch, the service connected users through a note-based messaging system, but after launch, user feedback called for a chat feature that allowed real-time conversations. While notes worked by loading and checking written messages, chat required messages from the other person to appear instantly, so the existing data model and the overall way data was received had to be changed.
Problem Solution
I reused as much of the existing note model code as possible to limit the scope of changes, focusing on the parts that needed real-time data. I used Firestore's real-time updates to receive new messages instantly and changed the code to reflect the received data on screen with RxSwift. As a result, we were able to switch from notes to real-time chat while the service was running, without major disruption to the existing structure. Through this process, I gained experience turning user feedback into changes in service structure, and came to understand real-time data handling and the importance of designs that reuse existing code to adapt to changing requirements.
Dynamic Bubble Sizing and Pinning to the Latest Message
Problem Identification
Chat bubbles had a fixed size regardless of message length, which made the screen look awkward. In addition, the chat screen needed to show the most recent message immediately upon entry regardless of the number of messages, but it was hard to tell when to run the scroll code after tableView(cellForRowAt), so I couldn't find the right moment to move to the last message.
Problem Solution
For bubble width, instead of fixing a trailing constraint on the message label, I adjusted the constraints of the adjacent time label (dateLabel) so the message label itself could stretch flexibly with its content. For height, I set the label's numberOfLines to 0 and applied UITableView.automaticDimension in heightForRowAt so cell heights adjust automatically to message length. To pin the latest message, rather than searching for the exact call timing, I followed the flow in which reloadData() is called whenever data updates in real time, found a function to run afterward, and used a scroll-to-last-message function so users can always focus on the most recent conversation. Through this process, I came to understand UITableView's cell creation and layout flow and how Auto Layout calculates dynamic sizes, and gained the ability to solve layout issues structurally on screens with variable content.
