쪽지 방식에서 실시간 채팅 모델로 전환
문제 인식
서비스 출시 당시에는 사용자 간 연결을 쪽지 방식으로 제공했지만, 출시 이후 사용자 의견을 통해 실시간으로 대화할 수 있는 채팅 방식으로 바꿔 달라는 요구가 생겼습니다. 쪽지는 작성한 메시지를 불러와 확인하는 구조인 반면 채팅은 상대의 메시지를 즉시 확인할 수 있어야 하므로, 기존 데이터 모델과 데이터 수신 방식 전반의 수정이 필요했습니다.
문제 해결
기존 쪽지 모델 코드를 최대한 재활용해 변경 범위를 줄이고, 실시간 데이터 수신이 필요한 부분을 중심으로 수정했습니다. Firestore의 실시간 업데이트 기능을 활용해 새 메시지를 즉시 받아오도록 구현하고, RxSwift로 수신한 데이터를 화면에 반영하도록 코드를 변경했습니다. 그 결과 서비스 운영 중에도 기존 구조를 크게 흔들지 않고 쪽지에서 실시간 채팅으로 전환할 수 있었습니다. 이 과정을 통해 사용자 피드백을 서비스 구조 변경으로 연결하는 경험을 쌓았고, 기존 코드를 재활용하며 요구사항 변화에 대응하는 설계의 중요성과 실시간 데이터 처리 방식을 이해하게 되었습니다.
채팅 길이에 따른 동적 크기 조절 및 마지막 채팅 위치 고정
문제 인식
채팅 메시지가 길든 짧든 말풍선 크기가 고정되어 있어 화면이 어색해 보이는 문제가 있었습니다. 또한 채팅 화면에 진입하면 채팅 개수와 관계없이 가장 마지막 메시지를 바로 보여줘야 했는데, tableView(cellForRowAt) 이후에 어떤 시점에 스크롤 코드를 실행해야 하는지 알기 어려워 마지막 채팅으로 이동시키는 시점을 잡지 못했습니다.
문제 해결
말풍선 너비는 메시지 라벨에 trailing 제약을 고정하지 않고 옆에 배치된 시간 라벨(dateLabel)의 제약을 조정해, 라벨 자체가 내용 길이에 따라 유연하게 늘어나도록 구성했습니다. 높이는 라벨의 numberOfLines를 0으로 설정하고 heightForRowAt에 UITableView.automaticDimension을 적용해 메시지 길이에 맞게 셀 높이가 자동으로 조절되도록 했습니다. 마지막 채팅 고정은 호출 시점을 직접 찾는 대신, 데이터가 실시간으로 갱신될 때마다 reloadData()가 호출되는 흐름에 맞춰 이후 실행할 함수를 찾아 적용했고, 마지막 메시지로 스크롤 이동하는 함수를 활용해 항상 가장 최근 대화에 집중할 수 있게 했습니다. 이 과정을 통해 UITableView의 셀 생성·레이아웃 흐름과 Auto Layout의 동적 크기 계산 방식을 이해하게 되었고, 이후 가변 콘텐츠 화면에서도 레이아웃 문제를 구조적으로 해결하는 역량을 갖추게 되었습니다.
